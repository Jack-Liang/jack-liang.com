> **系列说明**：这个系列写我在开发里反复验证过的基本规律。不追新概念，只讲那些早晚会再次应验的东西。

> **TL;DR**：配置表不是建完就完，是要被找到的。
>
> 有一次接手一个项目的维护。打开 SE11 一搜
> Z*，几十张配置表躺在那里：ZCONFIG01、ZTEMP、Z_BATCH，还有两张名字差不多、没人说得出区别的。建表的人有的已经离职了。业务说"我之前改过一个字段，是在某张表里改的"——没人记得是哪张。这篇讲一个反直觉的判断：配置表泛滥本身是技术债。再加五个做法和一份自查清单。

## 一、接手时的一堆"野表"

有一次接手一个项目的维护。

打开 SE11 一搜
Z*，几十张配置表躺在那里：ZCONFIG01、ZTEMP、Z_BATCH、Z_TEST_001，还有 ZFI_CONFIG
和 ZFI_TBL_CFG
两张，名字差不多，问了一圈没人说得出区别。有几张表的建表人已经离职了。

我想先找份清单看看系统里到底有哪些配置表、各自干嘛的。Confluence
翻了半天，找到几篇接口说明，没有配置表清单这种东西。

去问业务。业务说："我之前改过一个字段，是在某张表里改的。"哪张？不记得了。SE16N
一张一张打开看字段，像翻别人家的抽屉。

这些表有个共同点：建的时候随手建，建完没人登记，没人维护，三个月后没人记得。我后来管它们叫"野表"。

我以前觉得，建张配置表很容易，多建几张没什么。接手了这次才明白：每多一张表，就多一份要有人命名、有人登记、有人负责的东西。建的时候没人拦，找的时候没人找得到——问题都留给了后面的人。

## 二、建表五分钟，治理一辈子

SE11
里建一张表，五分钟，没有任何流程拦得住。但从那天起，这张表就需要：一个看得懂的名字、一句说清用途的话、一个负责人、一份维护说明，每次系统升级还得带着它迁移。

野兔是"泛滥"最经典的教材：一百多年前有人放跑了二十来只，几十年里繁殖到几亿只，草原被啃秃，花了几十年治理都没根除。配置表的繁殖速度跟兔子没法比，但逻辑一样——每多一张，都永久加一分治理成本。

N 张表就是 N 倍治理负担。负担不会消失，只会转移——从建表的人转移到接手的人。

还有一个问题：表该建在哪。"这个大家都可能用，放 ZCOMMON
吧"——这话听着合理，其实判断标准错了。大家都用、但属于财务域，就该放
ZFI_COMMON；真正不属于任何业务域的，比如货币、日期这种，才进
ZCOMMON_BASE。判断标准是业务归属，不是用的人多不多。放错地方的表，和野表差不多。

治理的关键动作只有一个：登记造册。建一张配置表目录表
ZTC_REGISTRY，每张配置表一行：

```abap
" ZTC_REGISTRY —— 配置表目录
TABNAME          " 配置表名，主键
PURPOSE          " 用途，一两句话，必填
OWNER            " 负责人，换人时更新
CREATED_ON       " 创建日期
RELATED_PROGRAMS " 关联程序
MAINT_GUIDE      " 什么场景该改、什么不能改
STATUS           " ACTIVE / OBSOLETE
```

两条硬规则：新建配置表当天登记，写进 Code Review 检查项；接手的人第一件事就是
SELECT 这张表，系统里有哪些配置表、归谁管，一次看清。

这就是把配置表从个人记忆变成系统记忆。和
[03 篇](/blog/dev-first-principles-03-single-source-of-truth/)
是同一个思想：一个数据只能有一个源头——ZTC_REGISTRY
就是"系统里有哪些配置表"这个问题的源头。

你可能觉得：建张表还要登记，太麻烦了。建的时候麻烦五分钟，和接手的时候翻三天，哪个划算不难算。

## 三、没建档的设备，坏了没人修

这事工厂里早就有答案。一台设备进厂，第一件事不是开机用，是建档：编号、名称、负责人、保养记录，全记在设备台账上。

反过来，没建档的设备什么样？坏了没人修，因为不知道归谁管；搬迁丢了没人找，因为台账上根本没这东西；审计盘点时角落里翻出一台机器，谁也不知道是谁买的、还能不能用。

配置表就是系统里的设备，ZTC_REGISTRY
就是设备台账。登记看着像多此一举，真到要改配置、要交接、要升级那天，查得到和查不到，就是有没有台账的区别。

## 四、五个做法

落到 ABAP，按使用频率排。

**1. ZTC_ 命名空间**。所有配置表统一 ZTC_ 前缀，前缀后面带业务域：ZTC_FI_
财务、ZTC_MM_ 物料、ZTC_SD_ 销售。SE11 一搜 ZTC*
就能列出全部配置表，看名字就知道它归哪个域。相比之下，ZMYCONFIG、ZTEMP
这种名字，等于宣布"不想让人找到"。

**2.
登记造册**。上一节说了，不再重复。补一句流程上的：登记表本身也要有人管，OWNER
换人时更新，不然登记表自己也会变成野表。

**3. Data Element 文档必填**。字段建了 Data Element，顺手把 DOCUMENTATION
写上，用户光标放字段上按 F1 就能看到说明。注释会过期，Data Element
不会。[08 篇](/blog/dev-first-principles-08-magic-numbers/)
的自查清单里提过这条，这里展开成做法。

**4. 新需求先查标准 Customizing**。S/4 里现成的配置表非常多：T001 公司代码、T005
国家、T009
财年变式。接到需求先查标准表里能不能配，确实没有再自建。反例也见过：标准表能配的东西，硬建一张
ZMY_COMPANY_CODE，三个月后自己也不认得这张表。

**5. 生命周期管理**。不再用的配置表，STATUS 改成
OBSOLETE，不删——物理删除可能砸到还在读它的程序。每季度过一遍
ZTC_REGISTRY，半年没人动的表拉出来问业务还要不要。

再进一步，可以做张"表 →
程序"的反向清单：写个小工具扫程序源码里出现的表名，哪张表被哪些程序读，结构化的对照存下来。接手时输入表名，立刻看到谁在用它。这比全局
grep 强，grep 出来几百条里一大半是注释和无关命中。

你可能想问：都说怕泛滥，那什么情况才配建表？[08 篇](/blog/dev-first-principles-08-magic-numbers/)
的分级还作数：永远不变的写
CONSTANTS，业务天天改的去接标准主数据，只有一年调一两次、业务想自己上 SM30
改的参数，才轮到配置表。配置表是稀缺品，不是垃圾桶。

自查清单，Code Review 时过一遍：

1. 配置表统一 ZTC_ 前缀，前缀后带业务域
2. 新建配置表当天登记 ZTC_REGISTRY，OWNER 必填
3. 字段建了 Data Element，DOCUMENTATION 写了
4. 新需求先查标准 Customizing，没有再自建
5. 不用的表标记 OBSOLETE，不物理删除

反模式也说一句：ZTEMP、Z_TEST_001
这种名字，和建完不登记，是同一件事的两个侧面——从起名那一刻起，就没打算让第二个人找到它。

## 五、写在最后

**配置表不是建完就完，是要被找到的。**

泛滥的麻烦不在表的数量，在于没人说得清系统里到底有哪些表。治理的目标也不是少建表，是每张表都查得到、找得着人、说得清用途。

[08 篇](/blog/dev-first-principles-08-magic-numbers/)
把字面量收进常量，这篇把配置表收进登记册——干的是同一件事：让信息待在能被找到的地方。

下一篇讲代码本身。配置表是数据层的"可被找到"，下一篇是代码层的：命名和结构组织好了，代码自己就是导航，不用先翻文档。
