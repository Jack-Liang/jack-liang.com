> **系列说明**：这个系列记录我在开发中感知到的、经得起反复验证的基本规律。不追新概念，只讲那些"早晚会再次应验"的东西。

> **TL;DR**：用户友好化和消息保留是两件事；包装不要替换原始消息。
>
> 业务部门一句"同步失败"，你翻了一上午日志找不到具体哪步失败——这篇讲一个反直觉的判断：**给用户"友好提示"反而让排障变难**。核心原则：**包装不替换，累加不丢弃**。配 S/4 平台自开发的具体做法（FM 嵌套 / 应用日志 / BAdI / OData）+ 跨语言对照（Java cause chain / Go %w / Python raise from），让你下次写 catch 块时知道——**怎么既能友好，又不丢信息**。

## 一、现象：被"操作失败"折磨的那个上午

**你**有没有过这种排查——一个跨系统的订单同步问题。

业务部门反馈："订单同步失败了。"再问，"提示什么？""提示'同步失败：请联系管理员'。"

**我手里就这七个字。**

打开应用日志（SLG1），翻到对应时间。**有的**。但每一层都是 catch + log + 抛自己的"友好"消息。最外层 catch 把所有消息包装成"同步失败"。

我点进最外层日志，想看具体哪步失败——**没了**。

点进下一层："订单同步服务失败"。再下一层："订单校验失败"。再下一层："校验失败"。再下一层……

**原始消息"外部系统返回 HTTP 503，retry 3 次后超时"——完全丢了**。

**你**能想象那个上午——我花了一整个上午，**逐层翻代码、逐层追原始抛点**。最后才在最深一层的 try-catch 里找到那个被吞掉的根因。

**"我曾以为"**：给用户友好提示是好事——总比丢一堆技术术语强。
**"后来发现"**：**友好化和丢弃原始消息，是两件事**。前者是"包装"，后者是"替换"——**你**以为是包装，其实是替换。

从那以后，**你**看 catch 块的眼神也会变——**只 log 不 rethrow 的，是事故现场**。

---

## 二、原理：为什么"友好化"反而害了排障

这背后有一个朴素的原则：**包装不要替换，累加不要丢弃**。

抛出点是消息的"**源**"——和你 03 篇讲的 SSoT 是同源思想：**关键事实必须有一个权威的、不可替代的记录点**。错误消息的权威记录点，就是最初抛出的那一行。

下游每一层可以做的事：

- ✅ **追加**自己的上下文："我调订单校验服务失败，原因是 ..."
- ✅ **翻译**消息给特定受众："HTTP 503"翻译成"外部系统暂时不可用"
- ❌ **替换**原始消息：用"同步失败"覆盖"HTTP 503"
- ❌ **吞掉**异常：catch 后 log 一下，让程序"继续"

**你**下次写 catch 块前，可以先问自己：**这四类我做的是哪种？**

为什么"替换"和"吞掉"会害了排障？

因为**排障需要的是"链"，不是"点"**。一个错误从最深处冒出来，穿过校验、穿过服务、穿过接口、穿过 UI，每一层都该保留上一层说了什么。**到最后，运维或开发者看到的应该是"一条链"**——从最外层的用户提示，到最内层的根因。

但很多代码的实际表现是"**断链**"——到外层只剩一行"操作失败"。**这正是 01 篇讲的"安静的低级错误"的另一种形态**——错误活着，但失去了所有诊断信息。

还有第二个反直觉点：**用户友好化不等于替换**。

"给用户友好提示"完全可以做——**但要双轨**：

- **技术消息**给运维/开发者（保留原始，能定位）
- **友好消息**给最终用户（用业务语言说"操作失败，请稍后重试"）

OData 服务返回的 `message` + `innererror` 就是这个思路——前端给用户看 `message`，开发者查 `innererror` 里的 `errordetails`。**两条线，一条都不丢**。

把这个规律总结成一句，**你**写 catch 时可以默念：

> **包装不要替换，累加不要丢弃。友好化和保留信息，是两件不冲突的事。**

## 三、呼应：这个道理在开发之外早就被验证过

**跨语言对照**（看本质）：

| 语言 | 保留原始消息的做法 |
| --- | --- |
| Java | `new RuntimeException("我调它失败", originalException)` 保留 cause |
| Python | `raise NewError("...") from originalError` |
| Go | `fmt.Errorf("...: %w", err)` 配合 `errors.Is / As` |
| Rust | `?` + thiserror 自动保留 chain |
| JS（ES2022+） | `new Error("...", { cause: originalError })` |

本质都是**同一件事：错误链不能断，根因不能丢**。SAP / ABAP 在这件事上其实不落后——`sy-msgid / sy-msgno / sy-msgv1-4` 早就设计好了消息链，**问题不是工具不行，是人没用到**。

**医学的体检报告和病历**也是这个结构。

体检报告（给用户看）写"血脂偏高，建议复查"——友好、易懂、不吓人。病历（给医生看）写"LDL 4.7 mmol/L，伴颈动脉斑块"——精确、可追溯、能决策。**两份记录同一个事实，互不替代**。

把"体检报告"和"病历"合并成一份"血脂不太好"——表面上看更友好，实际**既不能帮用户理解，也不能帮医生决策**。

**法律的判决书和庭审记录**也是同一套。判决书给当事人（友好、结论性），庭审记录存档（原始、过程性）。**判决书不替代庭审记录**——后者是溯源依据。

医学、法律、跨语言工程，**四个看似无关的领域，用着同一个底层动作：把"给最终用户的友好版本"和"给专业人士的原始版本"分两轨保留，原始信息永不丢失。**

## 四、实践：把原理变成清单

落到日常，我把"消息不丢"拆成 S/4 平台自开发的 3 个具体做法 + 1 份通用清单。

### 场景 A：FM 嵌套调用

被调 FM 抛消息，调它的 FM catch 后怎么办？

- ❌ `MESSAGE '操作失败' TYPE 'E'.` —— 原始消息丢了
- ✅ `MESSAGE ID sy-msgid TYPE 'E' NUMBER sy-msgno WITH sy-msgv1 sy-msgv2 sy-msgv3 sy-msgv4.` —— 完整保留
- ✅✅ `MESSAGE e001(zx) WITH '订单同步' RAISING.` —— **包一层自己的上下文**："订单同步失败"，**同时把原始消息传下去**

**关键习惯**：catch 块里**先存 sy-msgid / msgno / msgv1-4，再做自己的事**，别图省事用 `MESSAGE 'xxx'`。

### 场景 B：后台作业 / 应用日志（SM37 / SLG1）

异步场景下，应用日志是事后唯一的诊断入口。

- 用 `BAL_LOG_MSG_ADD` 写**消息类 + 参数**：`msgid = 'ZORDER'`, `msgno = '001'`, `msgv1 = '订单号 12345'`
- 关键：**用消息类（SE91）而不是硬编码文本**。**ID 不变文本可变**，将来翻译、升级、复用都方便
- 出错时运维 grep 消息类 ID（如 `ZORDER 001`），**直接定位到抛出点 + 当时的参数**

### 场景 C：BAdI / Enhancement 实现

自开发 BAdI 实现里出错时怎么办？

- ❌ `RETURN.` —— **静默退出**，标准程序以为 BAdI 成功了，最诡异的那类 Bug
- ✅ `MESSAGE e001(zx) RAISING.` —— 抛出去让标准程序感知
- ✅✅ 在 BAdI 入口先 `CHECK sy-subrc = 0`（调标准方法），失败就 `RAISING`

**BAdI 失败的代价不是"BAdI 报错"，而是"BAdI 报错但没人知道"**——因为标准程序会按"成功"继续往下走。

### 场景 D：OData / Web API

OData 错误返回结构本身支持双轨：

```json
{
  "error": {
    "message": { "lang": "zh", "value": "订单同步失败，请稍后重试" },
    "innererror": {
      "errordetails": [
        { "code": "ZORDER/001", "message": "HTTP 503 retry 3 times", "propertyref": "OrderNo" }
      ]
    }
  }
}
```

- **`message`** 给前端 / 用户看（友好）
- **`innererror`** 给运维 / 开发者看（原始）

**两条线都保留，互不替代**。

### 通用清单（任何 catch 块都过一遍）

1. **catch 必 rethrow，绝不只 log**——`catch { log; rethrow }`，`catch { log; 继续 }` 是事故现场
2. **log 与异常分离**——log 是给运维看的（事后查），异常是给调用方处理的（决定下一步）
3. **包装只追加，不替换**——加自己的上下文，别覆盖原始
4. **边界处做友好化，系统内保持原始**——只有跨系统/跨用户边界才翻译，内部传递别动
5. **ID 优先于文本**——用消息类 ID 而不是硬编码消息文本，方便检索和升级

**你**下次写 catch 块时，可以按这 5 条过一遍——**只要漏掉一条，事故现场就在酝酿**。

## 五、小结

> **包装不要替换，累加不要丢弃。**
> **友好化和保留信息，是两件不冲突的事。**

它给了我们一个反直觉的判断：**给用户友好提示反而害了排障，根因是"友好化"和"丢弃原始"被混为一谈**。分开两者——用户得到友好提示，开发者得到诊断信息，**两者兼得**。

它还呼应了 01 篇的主题：**消息丢失 = 安静的低级错误**。诡异 Bug 偏爱静默的错误，**消息链断掉 = Bug 穿上隐身衣**。

**你**下次写 catch 时，记住这两个字——**加，不换**。原消息保留，你的同事才有机会帮你定位。

—— 这是《开发第一性原理》系列的**第五篇**，也是"代码如何处理失败"主题的开篇。

下一篇，想聊聊"**异常和边界情况不是'特殊情况'**"——同样是处理失败，但这次讲的是**事前防御**。
