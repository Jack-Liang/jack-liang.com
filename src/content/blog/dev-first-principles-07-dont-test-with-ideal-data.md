## 一、测试全绿，上线照样 dump

上篇讲过一次除零 dump。这篇讲它的下半集。

那次之后我补了教训：把计算逻辑抽成一个 FM，规规矩矩写了 ABAP Unit。SETUP
里造数据，三个测试方法，断言齐全，跑起来全绿。

我放心了。上线一周，dump。

还是除零。dump 的那行数据，分母是 0，和 06
里同一个病根。而我的三个测试方法，金额是一百、两百、三百——客户都有、字段都齐、分母都大于零。

问题不在测试框架，不在断言写法，在数据。测试数据是我坐在工位上想出来的，真实数据是业务在系统里长出来的。

那次之后我改了看法：**测试通过 ≠
代码能跑**。测试通过只说明一件事——我用想象的数据验证过代码。真实数据来了会怎样，代码没答应过。

## 二、想象的数据有三个系统性偏差

开发者的测试数据为什么靠不住？因为它有三个倾向：

- 全是"漂亮的"：字段都填、格式都对、长度都够
- 全是"正常的"：金额大于零、内表不为空、SELECT 都查得到
- 全是"我知道的"：我见过的数据形态，才造得出来

真实数据在这三个方向上都是反的。空的、零的、超长的、带全角字符的、查不到的——业务里天天见，06
聊过这个清单。所以 100 个正常用例全过，也不等于代码能跑。按覆盖率的算法说：**0
个边界用例 + 100 个正常用例 = 0% 真实覆盖。**

你可能想问：真实数据长什么样，我哪知道？

知道的办法很简单：SE16N
打开业务表，翻到最脏的几行，照着抄进测试。哪个客户编码带空格，哪个金额里有千分位逗号，哪个描述是半角问号——测试数据就按这个造，别在工位上编。06
说"想到边界"靠问业务，这篇补一句："测到边界"靠抄业务。

你可能觉得：边界用例写起来费时间。

一个 FM 也就四五个场景：正常、零、负、超长、找不到。每个场景一个测试方法，一批
FM 一个下午能测完。和上线后排查一周的代价比，这便宜得太多了。

## 三、新药不能只在健康人身上试

开发之外，"理想化数据"的坑，医药行业掉得最深。

新药上市前要做临床试验。一期在健康志愿者身上做：年轻、没病、肝肾功能正常——数据漂亮，副作用少，通过得也快。但一种药只在健康人身上试过就上市，谁都不敢。所以还要三期，在真实的病人身上做：有并发症的、同时在吃别的药的、肝肾功能本来就不全的。上市之后还有四期，继续盯真实世界里的不良反应。

因为药最终要进的是真实世界。程序也一样——它上线后面对的是业务数据。

在健康人身上安全，只说明它在一个理想环境里安全。程序在漂亮数据里能跑，也一样。

## 四、Function 和 Form 怎么测

落到 ABAP，按 02 篇"按职责切"的思路，分三种东西测。

**纯函数**——输入参数进、输出参数出，不碰数据库的。这种最好测，是 ABAP Unit
的主战场。每个数据场景一个测试方法，命名就把场景说清楚：

```abap
CLASS ltcl_tax_calc DEFINITION FINAL FOR TESTING
  DURATION SHORT RISK LEVEL HARMLESS.
  PRIVATE SECTION.
    METHODS:
      normal_amount   FOR TESTING,
      zero_amount     FOR TESTING,   " 接 06 的五条边界
      negative_amount FOR TESTING.
ENDCLASS.

METHOD zero_amount.
  DATA(lv_tax) = zcl_tax=>calculate( iv_amount = 0 ).
  cl_abap_unit_assert=>assert_equals(
    act = lv_tax
    exp = 0
    msg = '零金额应返回零税额，不应抛错' ).
ENDMETHOD.
```

happy path 那一个方法，作用接近语法检查。真正干活的是后面几个。

**带副作用的**——要读数据库、写自建表的。照样写 ABAP
Unit：造数、执行、断言，跑完测试框架自动回滚，不污染数据。这类测试断言的是数据正确性——读出来的和写进去的对不对，不是流程跑没跑通。

**Form 和 Smart
Forms**——最麻烦，"数据对不对"和"长得对不对"混在一起。办法还是拆：数据准备一个
FM，渲染一个 Form。FM 可以测，Form 的字段映射用 Adobe Forms
的测试功能核一遍。但"打出来好不好看"没有黄金样本对照，只能靠人眼——这点我目前也没什么好办法。

最后是给每个测试类过一遍的清单：

1. 测试类里有 ABAP Unit，不是"我手测过了"
2. 场景覆盖 06 那五条：空 / 零 / 负 / 超长 / 找不到
3. 至少一行数据是从业务表里抄的真实数据
4. 改完代码跑过回归，旧用例全绿
5. 测试代码也被 review——测试代码也是代码

## 五、写在最后

**测试通过 ≠ 代码能跑。**

它只说明一件事：你想出来的数据，代码接住了。真实数据接不接得住，取决于造测试数据的时候，是坐在工位上编，还是去业务表里抄。
