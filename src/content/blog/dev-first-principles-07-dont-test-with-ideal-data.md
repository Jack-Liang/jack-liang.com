## 一、现象：测试时稳稳的，上线一周后 dump

有一次自开发一个对账单 ALV 报表。

测试时跑得稳稳的——订单几百条，金额从几十到上万，我自己的测试数据全是"漂亮"的数据：客户都有、金额都> 0、字段都填齐。

**上线一周后，dump**。

你可能也遇到过类似的经历——**你**自测时一切正常，上线后报表里却冒出几条"不可能出现"的脏数据。排查下来，几乎都是同一个原因：**测试数据是"我以为的"，真实数据是"业务给的"**——两者不一样。

排查后发现：业务用了"过滤参数"，某个客户**没在任何订单里**——ALV 显示正常，但分母为零（见 06 篇案例）。

我后来想：**如果测试时加一条"空数据"用例，dump 根本不会发生**。

**"我曾以为"**：测试通过 = 代码能跑。**"后来发现"**：测试通过 = **我用想象的数据测的代码能跑**，**不是真实数据下的代码能跑**。

**测试数据是开发者想象的，真实数据是业务给的——两者不一样。**

## 二、原理：测试金字塔 + ABAP Unit 实战

测试的本质是**用有限数据验证代码对真实数据的应对能力**。但开发者写测试时，**数据是"想象"的**——常常是"漂亮的"、"理想化的"。

**反直觉点**：

- ✅ 100 个正常 case 通过 ≠ 代码能跑
- ❌ **0 个边界 case + 100 个正常 case** = 0% 真实覆盖
- ❌ 测试数据是"我以为的"，不是"业务给的"

**测试金字塔**（在 ABAP 项目里的应用）：

```
        /\
       /  \         系统测试（eCATT，跑完整流程）
      /----\        —— 少而精，覆盖关键路径
     /------\
    /--------\      集成测试（多 FM / 多 Class 联调）
   /----------\     —— 适度
  /------------\
 /--------------\   单元测试（ABAP Unit，单 FM / Class）
——————————————————————  —— 多而细，**这里是反直觉点的主战场**
```

**最容易被跳过的是底层单元测试**——因为"简单"、"我自己测过"。但**简单代码 × 真实数据 = 未知**。

你可能觉得"简单代码有什么好测的"——**你**会惊讶地发现：上线后 80% 的 bug 来自你"以为"正确的那段代码。

### ABAP Unit 实战

**你**写 ABAP Unit 时，是不是也只测了 happy path？**你**会发现：边界 case 才是 ABAP Unit 真正的价值所在。

**Function Module 测试类**（最常见的场景）：

```abap
"被测 FM
FUNCTION zfi_ar_invoice_calculate.
  "输入：iv_amount TYPE p DECIMALS 2
  "输出：ev_tax TYPE p DECIMALS 2
  "逻辑：ev_tax = iv_amount * '0.13'.
  "     边界：iv_amount = 0 时 ev_tax = 0（不抛错）
ENDFUNCTION.

"本地测试类（SE37 里 test 功能）
CLASS ltcl_invoice_test DEFINITION FINAL FOR TESTING
  DURATION SHORT RISK LEVEL HARMLESS.
  PRIVATE SECTION.
    METHODS:
      test_normal   FOR TESTING,
      test_zero     FOR TESTING,   " ← 边界
      test_negative FOR TESTING,   " ← 边界
      test_null     FOR TESTING.   " ← 边界
ENDCLASS.

CLASS ltcl_invoice_test IMPLEMENTATION.
  METHOD test_normal.
    DATA: lv_amount TYPE p DECIMALS 2 VALUE '100.00',
          lv_tax    TYPE p DECIMALS 2.
    zfi_ar_invoice_calculate(
      EXPORTING iv_amount = lv_amount
      IMPORTING ev_tax    = lv_tax ).
    cl_abap_unit_assert=>assert_equals(
      act = lv_tax
      exp = '13.00'
      msg = '正常金额税额错误' ).
  ENDMETHOD.

  METHOD test_zero.
    DATA: lv_amount TYPE p DECIMALS 2 VALUE '0',
          lv_tax    TYPE p DECIMALS 2.
    zfi_ar_invoice_calculate(
      EXPORTING iv_amount = lv_amount
      IMPORTING ev_tax    = lv_tax ).
    cl_abap_unit_assert=>assert_equals(
      act = lv_tax
      exp = '0'
      msg = '零金额应返回零税额（不应抛错）' ).
  ENDMETHOD.
ENDCLASS.
```

**关键**：**每个测试方法对应一个数据场景**（正常、零、负、空）。**只测 happy path 等于没测**。

### Function 怎么测

**你**下次切 Function 时，可以按这三层判断——纯函数 / 有副作用 / 包装层，不同层测法不同。

按 02 篇"按职责切"原则，把 Function 分层：

| 层次 | 测什么 | 怎么测 |
| --- | --- | --- |
| **纯函数**（输入→输出，无副作用） | 各种数据场景 | ABAP Unit |
| **有副作用**（DB 操作 / 调用外部） | 数据正确性 | ABAP Unit + 测试数据回滚 |
| **包装层**（调用其他 FM） | 调用参数正确 | ABAP Unit mock 依赖 |

**关键习惯**：**只测"输入 → 输出"对的，不测"实际数据流通过"对的**——后者是集成测试的事。

### Form 怎么测（最痛）

**Form 测试最让你头疼**——**你**可能试过各种 mock、对比脚本，最后发现显示效果只能肉眼看——没办法，这是现实。

Form 测试难点：**显示效果**和**数据流**两件事混在一起。

**最佳实践**：**拆"数据准备" + "渲染"两段**——又是 02 篇"按职责切"。

```abap
"❌ 所有逻辑混在 Form 里
"Form 里读内表、计算、循环输出、页眉页脚

"✅ 拆分
"1) 数据准备 FM（可测）
"   zfi_ar_invoice_data_prepare
"   输入：订单号 → 输出：准备好渲染的内表
"   测：ABAP Unit 测数据正确性

"2) 渲染（用 SE38 测）
"   zfi_ar_invoice_render
"   调用 1）拿数据 + Form 显示
"   测：人工核对 PDF / SPAD 测试页
```

**Form 显示效果的测试**：
- **Adobe Forms**：用 `FP_TEST_*` 系列 FM 测试字段映射
- **SAPscript**：只能肉眼看（没办法，这是现实）
- **SPAD / RSTXLDMC**：测试打印机驱动兼容性

**Form 测试的真正痛点**："看上去对不对"没有**黄金 PDF 对照**——只能靠人眼。**Adobe Forms 相对好一些**（有 XML 调试输出），SAPscript 几乎是盲测。

## 三、呼应：这个道理在开发之外早就被验证过

**医学的"自查"**——医生写完病历自己检查，护士执行前再核对，**不是"反正 QA 会查"**。

**航空的起飞前 checklist**——飞行员起飞前**自己**过一遍清单，不依赖地面塔台。**"塔台会告诉我的"是要命的想法**。

**出版业的三审三校**——作者自校 + 编辑审校 + 终审，**不是"终审会把所有错的"**——前两校抓出 99% 的错。

**测试是开发者的责任，不是 QA 的责任**——**不是"QA 会查到的"**，是"我必须自己验证"。

**你**下次写完代码准备转测时，可以问自己一句：这是医生的"自查"，还是把责任全推给了 QA？

生活里也一样：厨师做完菜**自己先尝**——不是"客人吃了觉得好吃就行"。**公司体检套餐**也是强制执行——不是"反正不舒服会去医院"。

## 四、实践：把原理变成清单

### 编码完 5 分钟自测

**你**下次编码完，先别急着 push——按这 5 条过一遍：

| 序 | 检查项 | ☐ |
| --- | --- | --- |
| 1 | 我用 ABAP Unit 写了测试类（不是"我手测过了"） | ☐ |
| 2 | 测试覆盖了**空 / 零 / 负 / 超长 / 找不到**（接 06 的 5 条打勾） | ☐ |
| 3 | 至少 1 个**"业务真实数据"**的用例（不是我想象的"漂亮"数据） | ☐ |
| 4 | 改动后**跑过回归测试**（不是"应该没改坏"） | ☐ |
| 5 | **测试代码也被 review / 维护**（不是"测试代码不算代码"） | ☐ |

### 测试金字塔在 ABAP 的实践

**你**下次规划测试时，可以按这个金字塔分配精力——底层占大头，顶层只覆盖关键路径：

- **底层**（ABAP Unit）—— 数量多，每个 FM / Class 一个测试类
- **中层**（手工集成）—— 几个关键流程手测一次
- **顶层**（eCATT / 端到端）—— 1-2 个核心业务流（不追求全覆盖）

### 反模式

- ❌ "我手测过了"——**不算测试**
- ❌ 100 个正常 case + 0 个边界 case = **0% 真实覆盖**
- ❌ "测试代码不被当代码"——**测试代码也是代码**，要维护要 review
- ❌ "测试能通过 = 代码能跑"——**测试能通过 ≠ 代码能跑**
- ❌ "测试数据用最简单的"——**最简单的数据不会暴露问题**

## 五、小结

> **测试数据是想象的，真实数据是业务的——两者不一样。**
> **测试能通过 ≠ 代码能跑。**

它给了我们一个反直觉的判断：**测试通过是"我用想象数据验证过代码"，不是"代码能跑真实数据"**。**测试通过 ≠ 代码能跑**。

你下次写完测试准备转测前，先回头看一眼——**这 100 个测试用例里，有没有一个是"业务真实数据"？**如果全是"漂亮数据"，那 100 个全绿也不代表代码能跑。

它接过 06 篇的"想到边界"，讲"测到边界"——**想到 + 测到 = 完整闭环**。**只有思维没有测试，思维只是想法；只有测试没有思维，测试只是形式。**

**你**读完这篇，希望带走三件事——

1. **测试能通过 ≠ 代码能跑**——测试通过是"我用想象数据验证过"，不是"代码能跑真实数据"
2. **用真实业务数据测**——至少 1 个用例来自业务真实数据，不是开发者想象的"漂亮"数据
3. **想到边界 + 测到边界 = 闭环**——光想不测是纸上谈兵，光测不想是机械执行

下一篇，想聊聊"**配置表泛滥怎么治理**"——开发中到处都是"被埋没的信息"，魔术数（08）是一种，**配置表是另一种**。
