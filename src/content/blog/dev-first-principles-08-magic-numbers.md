> **系列说明**：这个系列写我在开发里反复验证过的基本规律。不追新概念，只讲那些早晚会再次应验的东西。

> **TL;DR**：魔术数 = 你现在记得，未来的你不记得。
>
> 你有没有遇到这样的情况，业务部门通知：状态码改了，'01'
> 现在是驳回，新建改成'04'。我打开程序，满眼
> 01、02、ZPR——开发的人早跑了，也没人统计过它们散在哪些程序里。这篇讲一个判断标准：这个值会变吗、多久一次、谁能改。再加五个经典做法和一份自查清单。

---

## 一、业务部门说：'01' 改成驳回了

有一次维护一个自开发报表。打开程序一看，满眼都是 '01'、'02'、'ZPR'、'ZSO'：

```abap
IF ls_order-status = '01'.
  "新建订单
ELSEIF ls_order-status = '02'.
  "已审核
ENDIF.

IF ls_order-doc_type = 'ZPR'.
  "采购订单
ENDIF.
```

写代码的时候知道 01 是新建、02 是已审核、ZPR
是采购。写代码的人三个月前早跑了。现在的我盯着
'01'，想不起来它是新建、已审核还是已驳回——只好去翻注释，注释还只写了前两行。

真正的麻烦在后面。业务部门说：我们改了状态码，'01' 现在是驳回，新建改成 '04'。

改就改吧。问题是这 01 散落在十几个程序里，没人统计过。我全局搜
'01'，出来几百条结果：状态码是 01，屏幕序号是 01，格式化出来的 01
也混在里面。只好逐个程序打开确认。改 5 处，改完心里一直打鼓：漏没漏？

## 二、这个值会变吗，多久一次，谁能改

魔术数问题表面是"该不该用常量"，往深一层问是三个问题：这个值会变吗？多久变一次？谁来改？

按这三个问题分，值的命运就三种。

永远不变的，写
CONSTANTS。状态码、文档类型这种，定义了就不动。偶尔调的——一年一两次，比如税率、审批阈值——放配置表，建
SM30
维护视图，让业务自己改。业务天天改的，别碰：那是客户、物料这类标准主数据，本来就有地方维护，自建表去接是重复造轮子。

判断方法很朴素：业务说要改
X，问一句"这个你多久改一次"。一年一两次的，配置表；天天改的，主数据；说"这个永远不会变"的，CONSTANTS。

你可能觉得：值反正不会变，直接写死省事，抽成常量不是多此一举？

省事是真省事，但省的是现在的你的事，坑的是未来的你。'01'
直接写在判断里，是给现在的你写的——你此刻记得它什么意思。常量定义里的 01
才是给未来的你写的：三年后维护的人，如果还是你，点一下跳转，就能看到定义常量的地方，还有注释帮助理解。
改一处全改，再也不用到处去找。

所以同一字面量出现第二次，我就抽常量。不为别的，就为未来那个一脸懵的自己少翻一次代码。

## 三、甲骨文没有释读表就是天书

这事不是代码独有的。考古学里有个词叫"释读"：出土的甲骨文刻的是什么、什么意思，几百年里学者一张一张做对照表，一个字一个字地认。没有这张对照表，甲骨文就是天书；有了它，三千年前的记账记录你今天读得懂。

我们代码里的 '01'，就是那个甲骨文字符。常量定义、ENUM、配置表，就是释读表。

别的语言一样：Java 的 static final、C# 的 enum、Go 的
iota。叫法不同，干的是同一件事——给裸值一个名字、一个归属、一个类型，让人不靠记忆也能读懂。

## 四、五个经典做法

落到 ABAP，按使用频率排。

**1. CONSTANTS
命名常量**。最基础的一个，命名是契约：lc_status_new，这样即便不写注释，也能通过字面命名猜个大概，不是
lc_01；用业务语言 lc_order_approved，不是技术缩写 lc_o_a。

```abap
CONSTANTS: lc_status_new      TYPE zstatus VALUE '01',
           lc_status_approved TYPE zstatus VALUE '02',
           lc_status_rejected TYPE zstatus VALUE '03'.

IF ls_order-status = lc_status_new.
```

**2. 集中存放**。抽到一个 Include 或常量类，全项目引用同一份定义。最怕的是程序 A
里 01 是新建、程序 B 里 02 是新建——各自定义，迟早不一致。

**3. Type-safe ENUM**。7.4 以上直接上：传错值编译就报错，还不用维护 VALUE。

```abap
TYPES: BEGIN OF ENUM ty_order_status,
         new, approved, rejected, canceled,
       END OF ENUM ty_order_status.

DATA: lv_status TYPE ty_order_status.
lv_status = approved.               " 程序内直接用常量名

IF lv_status = approved.
```

**4. 配置表 + SM30**。前面说过，一年调一两次的业务参数走这条路，程序里 SELECT
SINGLE 按有效期读，S/4 自开发的标配。

**5. 命名空间**。配置表统一 ZTC_ 前缀，常量统一
lc_域名_含义。看名字能猜出含义，比注释可靠。

你可能想问：业务常调的值，总不能每次都找我改代码吧？

对，那就别用 CONSTANTS，用配置表。但顺序别搞反：先用
CONSTANTS，业务真来敲门了，再升级成配置表。一上来就建表，配置表会泛滥——那是下一篇的话题。

自查清单，Code Review 时过一遍：

1. 同一字面量出现 ≥ 2 次，抽常量
2. 状态的合法集合，7.4+ 项目用 ENUM
3. 常量集中在一个 Include 或常量类，没有第二份定义
4. 业务可能调的值，走配置表 + SM30，不写死
5. 自开发表字段建了 Data Element，SE11 里看得到文档

反模式也说一句：注释里写"= 1 是新建"，或者用 lv_status = 1
这种变量冒充常量——都不如一个真常量。

## 五、写在最后

**字面量是给现在的自己写的，常量是给未来的自己写的。**

别指望未来的你记得今天写的东西——他不记得，这很正常。设计的时候就当他不记得来设计。

这和
[03 篇](/blog/dev-first-principles-03-single-source-of-truth/)是同一个思想：一个数据只能有一个源头。字面量
01
的含义，源头就该是常量定义那一处，而不是散落在十几段代码和注释里的几百份拷贝。

下一篇聊配置表泛滥。魔术数治理是把字面量收进常量，配置表治理是把这些"信息源"本身管住——被埋起来的信息，怎么挖出来，怎么不越埋越多。
