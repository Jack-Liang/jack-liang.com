先说最反直觉的那个数字。

同一份报表，同一个数据库，同一天同一台机器：**数据量 1,469 行时，纯 ABAP 比 AMDP 快 2.9 倍；数据量 10,140 行时，两者打平；只有按组织下钻、且子树有上万节点时，AMDP 才反超 10%。**（把 AMDP 一路优化到底之后，1,469 行那一档也只追到 2.4 倍。）

AMDP 的卖点一直是「把计算下推到 HANA，让数据库用自己的并行能力算」。理论上它应该碾压应用层循环，但这次没有——或者说，<Notation type="highlight" color="#fef08a">它只在「被消除的那部分成本占比足够大」时才赢</Notation>，而这个占比跟数据量强相关。

这篇把这件事拆到底：三条路径各自怎么实现、成本花在哪，以及一套下次可以直接照抄的八步实施方法。

# 需求本身并不复杂

业务口径一句话：把组织架构树拍平成一张宽表，每行一个组织，带它的完整层级路径。

- 树最深九级，但要**拍平成固定 21 列**：组织 ID、组织名称、9 组「层级 ID / 层级名称」、以及路径深度
- 同一层如果撞了（一个组织在同一层挂到多个父节点下），用 `-` 拼接，上级在前、含自身
- 支持两种取数模式：全公司全量，或按某个组织**向下钻取**（含自身及所有子孙，最多 10 层）
- 对外是一个 RFC，必须支持 `ROWSKIPS` / `ROWCOUNT` 分页，还要回一个 `EV_TOTAL` 给前端算总页数

数据源就三张 HRP 表：`HRP1000`（对象主数据）、`HRP1001`（层级关系）、`HRP9500`（层级码）。开发机上 1,469 个组织，测试机上 10,140 个——差 7 倍，后面会看到这个倍数能把所有结论翻一遍。

听起来是典型的「一条 SQL 或者一个循环就完事」的需求。麻烦在于 21 列的透视：九个层级要各自展开成 ID 和 NAME 两列，而 SQL 里没有「按层级列动态展开」这种语法——只能靠自连接十次，或者靠层级函数的 `hierarchy_level` 列。

![三条实现路径：数据在数据库层算完，还是拉到应用服务器再算](https://img.jack-liang.com/sap-org-hierarchy-amdp-vs-abap/three-paths.svg)

# 先把几个名词说清楚

这篇文章会出现五个词，不先对齐含义，后面全是空话。

| 名词 | 在哪一层 | 是什么 | 这次用它解决什么 |
|---|---|---|---|
| **AMDP** | ABAP 与 HANA 之间 | ABAP Managed Database Procedure。用 ABAP 类方法当容器，方法体里写 SQLScript，编译后变成 HANA 侧的存储过程/表函数 | 把 BFS、透视、分页全塞进数据库，一次调用出结果 |
| **表函数（Table Function）** | HANA | CDS 里的 `define table function`，带参数、返回表，可以被 ABAP 当数据源查 | 让 `select ... from zom_tf_hier_flat(p_keydate = ...)` 直接拿结果 |
| **SQLScript** | HANA | HANA 的过程语言。表变量 + 集合运算，能写 `count(*) over ()`、`limit/offset`、`string_agg`、`max(case)` | 它就是「用 SQL 写算法」的那个语言 |
| **BFS（广度优先遍历）** | 无所谓 | 按层推进的树遍历：先找子节点，再找子节点的子节点 | 用 10 次自连接模拟递归，把子树圈出来 |
| **HIERARCHY 函数** | HANA | HANA 2.0 内置的层级引擎，一条 `hierarchy(source(...) start where ...)` 直接出层级路径和层号 | 把「10 次自连接」压成一次调用 |

有一个前提必须先确认：**ABAP CDS 的 `define hierarchy` 在 7.52 上不可用**，它要 7.55 以上。本系统是 7.52，所以「用 CDS 层级视图优雅解决」这条路直接断了，只剩 HANA SQL 侧的 `HIERARCHY` 表函数可走。

## 为什么是 21 列

九级 × 2（ID + NAME）= 18，加上组织 ID、组织名称、路径深度 = 21。

透视是整个查询里最贵的一步：九个层级要各自 `max(case when lvl = n then ... end)` 拉成列，一共 19 路聚合（18 个层级列 + 路径深度）。这一步在 HANA 上要物化一遍，在 ABAP 里就是 19 次内表赋值——看起来不多，但乘上 10,140 行、再乘上每次请求，就成了主要成本。

# 三条路径，怎么落地

## 路径 A：纯 ABAP

思路最直白：把三张表读到应用服务器，内存里做 BFS，内存里逐行上溯祖先。

关键是**不要给每一行单独查数据库**。假如写成「每行一个 `select single` 上溯父节点」，那就是 10,140 行 × 平均 4 跳 = 4 万次数据库往返，必死。正确做法是先把 `HRP1001` 全读进内表，建两个排序索引（按子找父、按父找子），后面全是内存二分查找。

BFS 用 10 轮推进：第 n 轮拿第 n−1 轮的结果集去查「谁是它的子节点」，查到的丢进 HASH 去重，顺便记下层号。上溯祖先同理，用 HASH 防环——组织树里真的存在环，主数据维护错了就会有。

```abap
" 一次读全，之后全是内存操作
SELECT objid sobid FROM hrp1001 INTO TABLE @DATA(lt_edge)
  WHERE otype = 'O' AND sclas = 'O' AND begda <= @lv_keydate
    AND endda >= @lv_keydate AND histo = '1' AND plvar = '01'.

SORT lt_edge BY sobid objid.          " 按父找子
SORT lt_edge BY objid sobid.          " 按子找父
" 之后 LOOP + READ TABLE ... BINARY SEARCH，不再回库
```

这条路的优点只有两个：**没有固定开销**（不调用数据库过程、不切会话），**分页在内存里切得动**（基础表已经在内存了，切 20 行只拼 20 行）。

代价也很清楚：1 万行全量时，内表要装 3 万行边 + 1 万行主数据 + 1 万个输出行 × 21 列，十几 MB 起步，而且是**每个并发用户一份**。

## 路径 B：AMDP

把同一套算法用 SQLScript 重写。三步：

1. `lt_org` / `lt_edge` / `lt_lvl` 三个基础表变量（对应 ABAP 那三张表）
2. `lt_scope` 圈出要算的组织范围（全量 or 子树）
3. 祖先展开 + 透视，只针对页内组织

第三步是这里的巧思：**先分页，再展开祖先**。祖先展开是最贵的部分（11 次自连接），只给页内 20 行做，成本就从「1 万行 × 11 次连接」降到「20 行 × 11 次连接」。

```sql
-- 祖先展开只针对页内行：lt_h0 从 lt_page 出发，lt_h1..lt_h10 逐层向上
lt_h0 = select p.objid as node_id, p.objid as cur_id, 0 as hop from :lt_page as p;
-- lt_h1 = lt_h0 join lt_edge on lt_edge.node_id = lt_h0.cur_id ...
```

透视就用 19 路 `max(case)`：

```sql
select o.objid as org_id,
       max( case when l.lvl = 1 then l.node_id   end ) as l1_id,
       max( case when l.lvl = 1 then l.node_name end ) as l1_name,
       -- ... 到 l9
       cast( max( l.hop ) as integer ) as path_depth
  from :lt_org as o left outer join :lt_path as l on l.org_id = o.objid
 group by o.objid
```

同层的多个节点用 `string_agg(... order by ...)` 拼成 `A-B-C`，这就是「撞列用 `-` 连接」的实现。实测样例：`10000103 制造处`，深度 3，`L1=10000001 集团总部`、`L2=10000100 事业群A`、`L3=10000102-10000103 事业部A-制造处`。

## 路径 C：AMDP + HIERARCHY

路径 B 里的「10 次自连接圈子树」，可以换成 HANA 原生的层级引擎：

```sql
lt_sub = select distinct h.node_id as objid
           from hierarchy( source ( select e.parent_id,
                                           e.node_id
                                      from :lt_edge as e )
                           start where parent_id = :p_objid
                             and :p_objid <> '00000000'
                           sibling order by node_id
                           multiparent ) as h
          where h.hierarchy_level <= 10;
```

这个函数会给每行带上 `hierarchy_level`（层号）和 `hierarchy_rank`（同层排序），刚好是透视需要的输入。四个参数各有讲究：

- `source()` 里只能是**一个** select，不能放 union——试过会报 `invalid column name: NODE_ID`，因为 union 之后列名解析丢了
- `start where` 必须用 **`parent_id = 起点`**，不能用 `node_id = 起点`。用后者会把起点自己排除在外，顶层组织一行都出不来
- `multiparent` 是必须的：一个组织挂多个父节点是常态，不加这个参数会直接报错
- `sibling order by` 决定同层顺序，影响 `-` 拼接的顺序

# 分页这件事，改了三次才做对

这段值得单独讲：它一半关乎性能、一半关乎正确性，难的是后者——纯粹的 SQL 语义坑，而且**每一步看起来都对**。

先打个预防针：这一章是支线。它不改变选型结论，只负责解释那个 200 ms 的固定成本从哪来——赶时间的话可以直接跳到实测数据。

![分页实现的三代演进：从假分页到 exists 求交再到下推进子树构造](https://img.jack-liang.com/sap-org-hierarchy-amdp-vs-abap/paging-evolution.svg)

## 第一代：假分页

最初版本在 ABAP 侧切页：SQL 全取回来，`LOOP AT ... FROM s TO e` 切出当前页。

问题在于 `ROWSKIPS` / `ROWCOUNT` 是 RFC 接口的参数，在 ABAP 里切，就意味着取一页也要把 10,139 行全量搬回应用服务器——**测试机上取一页和取全部一样贵，都是 850 ms 上下**。省掉的只是「页外行的 21 列拼装」，那是总成本里很小的一块。

把 `limit / offset` 下推进表函数后，取 1 行降到 **207 ms**。这 200 ms 就是这条路绕不开的固定成本：圈子树、`count(*) over ()`、三个基础表变量物化，跟页长无关。

## 第二代：exists 求交

速度上来了，正确性掉下去了。`IV_OBJID` 传子树时，`EV_TOTAL` 比实际行数大 3。

根因是执行顺序：`count(*) over ()` 和 `limit/offset` 都作用在 `lt_scope` 上，而 `lt_scope` 还没跟组织主数据求交——最后输出时才 `inner join lt_org`。子树 BFS 从 `HRP1001` 收进来 3 个「有边但主数据无有效记录」的脏节点，于是总数偏大、offset 整体前移一行，**最后一页多回一行、且跟前一页重叠**。

修法是在翻页之前先求交：

```sql
lt_scope2 = select s.objid as objid
              from :lt_scope as s
             where exists ( select 1 from :lt_org as o
                             where o.objid = s.objid );
```

这里选 `exists` 而不是 `inner join` 是有意的：如果 `HRP1000` 因为有效期重叠出现同一 objid 多行，`inner join` 会把 scope 行放大，`exists` 不会。

正确性全部恢复。然后**代价来了**：开发机全量 90.3 → 103.5 ms（+13），测试机全量 409 → 490 ms（+78）。

## 定位：`where exists` 被按行执行

一开始我以为是「多了一步必然要付的钱」，差点就这么接受了。真正拆开是因为一个比例：

| 系统 | 行数 | `where exists` 增加的成本 |
|---|---|---|
| 开发机 | 1,469 | +13 ms |
| 测试机 | 10,140 | +78 ms |

行数比 7 倍，成本比 6 倍——**线性相关**。这说明 HANA 没有把这个相关子查询去关联（decorrelate）成 join，而是**逐行执行**了。

开发机上行数少，13 ms 混在抖动里没人发现；测试机上万行，就直接变成 20% 的回退。

## 第三代：过滤下推进构造

既然全量模式下 `lt_scope` 本来就等于 `lt_org`（不需要过滤），这个过滤只应该发生在下钻模式，而且应该**在构造 `lt_sub` 的时候就完成**：

```sql
lt_sub = select distinct h.node_id as objid
           from hierarchy( ... ) as h
          inner join :lt_org as o on o.objid = h.node_id
          where h.hierarchy_level <= 10;

lt_scope = select o.objid as objid from :lt_org as o where :p_objid = '00000000'
           union select objid from :lt_sub
           union select o.objid as objid from :lt_org as o
                  where o.objid = :p_objid;   -- 自身节点，顺带校验它在主数据里
```

一次 join 换掉 N 次 exists。全量模式零过滤成本，下钻模式脏节点在源头就被剔掉，`count(*) over ()` 与 `limit/offset` 直接落在最终行集上，分页仍然正确。

测试机全量从 477～502 回到 **405～430**，20% 的回退全部收回。

> 教训：`where exists` 在 HANA 上不一定是半连接（semi-join）。**判断依据不是「写法看起来像什么」，而是「成本随行数怎么变」**。线性 = 按行执行，常数 = 真的只算一次。

# 为什么 AMDP 没赢

这不是「HANA 不够快」，而是三个成本项的结构问题。

![两条成本曲线在 1 万行附近交叉](https://img.jack-liang.com/sap-org-hierarchy-amdp-vs-abap/cost-curve.svg)

## 一、AMDP 有一个压不掉的固定成本

大概 50 ms。表函数调用、SQLScript 执行计划、ABAP ↔ HANA 会话切换，这几项跟行数无关。1,469 行时它接近总成本的一半——所以开发机上怎么优化都赢不了 31 ms 的纯 ABAP。

纯 ABAP 没有这个固定成本。它的第一行数据从「`SELECT` 返回」那一刻就开始算，没有启动费。

## 二、AMDP 必须把整棵树物化，ABAP 不必

这是最本质的差异。

AMDP 拿到「每页 20 行」的需求，仍然要：读三张表 → 圈子树（或全表）→ `count(*) over ()` 算出总数 → `limit/offset` 切 20 行 → 给 20 行展开祖先 → 透视。

而纯 ABAP 的分页是**假分页**：三张基础表全读（这部分省不掉），但 21 列的拼装、排序、上溯祖先，真的只对页内 20 行做。

所以 AMDP 是「**固定成本 + 全量算一遍再切**」，ABAP 是「**无固定成本 + 只算页内行**」。数据量小的时候，后者的结构优势完胜。

## 三、斜率不同，交叉点在 1 万行

把两边的实测点拟合成曲线：

```
AMDP   ≈ 50 + 0.036 · n        (ms，n = 行数)
纯 ABAP ≈ 0.0019 · n^1.33
```

AMDP 的斜率是常数（每行约 36 µs），ABAP 是超线性的（指数约 1.33，来源是逐行上溯祖先 + 9 组字段拼装 + 最终排序）。两条线在 **n ≈ 10,140 处刚好重合，都是 415 ms**。

这就是「1 万行拐点」的量化版本。它不是玄学，是两条拟合线的交点。

<Notation type="box" color="#8b5cf6">所以「AMDP 更快吗」这个问题本身就问错了。正确的问题是：我的瓶颈在应用服务器的逐行处理上，还是在数据库的往返与物化上？</Notation>

补一个非性能的维度：AMDP 版本全量时只往 ABAP 回传 1 万行成品；纯 ABAP 版本要在应用服务器内存里同时装 3 万行边、1 万行主数据、1 万行输出，**每个并发用户一份**。真上生产、几十个人同时拉全量报表时，这个内存账会先炸。

# HIERARCHY 赢在哪，什么时候不赢

标题里「做对了什么」，全部答案都在这一章——不多，但都是实测的。

一开始我以为 HIERARCHY 是全面的性能升级——它确实把「10 次自连接 + 11 路 union」压成一次调用。开发机上全量省 26%、单页省 35%，看着很漂亮。

然后到测试机上，全量 **0%**。

原因是规模扫描暴露出来的：

| `P_OBJID` | 行数 | BFS 版 | HIERARCHY 版 | 变化 |
|---|---|---|---|---|
| `00000000`（全量） | 10,140 | 446.7 | 437.1 | −2% |
| `10000001` | 10,112 | 537.4 | **447.9** | **−17%** |
| `10000103` | 1,788 | 317.1 | 303.0 | −4% |
| `10000201` | 5 | 146.8 | 150.2 | +2% |

三条规律：

1. **收益只跟「递归要处理的节点数」成正比，跟总行数无关。** 子树 10,112 个节点时要跑 10 次全量 join，HIERARCHY 一次搞定，省 89 ms；只有 5 个节点的子树，什么都省不出来（甚至因为固定开销略慢 2%）。
2. **测试机的固定成本约 147 ms**——5 行的查询也要 146.8 ms，这部分由三张 HRP 表读取与三个基础表变量物化构成，跟 scope 算法完全无关。
3. **全量 446 ms 里，真正随行数变化的部分只有约 300 ms**，而那 300 ms 是祖先展开（11 次 join）+ `string_agg` + 19 路 `max(case)` 透视——**HIERARCHY 一点忙都帮不上**。

所以「HIERARCHY 让测试机也省三成」这个预测不成立。它在测试机上的真实价值只有一句话：**按组织下钻时省 17%**。

开发机上那句 −26% 也得改口径：全量模式根本不走递归，那 23 ms 的差距来自 BFS 版那 10 个 `lt_k1..lt_k10` 语句——它们是**无条件执行的 SQLScript 语句**，即使每层都返回空集，10 次 join + 11 路 union 的语句开销照样要付。换成 HIERARCHY 后只剩一次调用、返回空集，这笔空转开销就没了。

<Notation type="underline" color="#ef4444">优化的收益永远等于「被消除的那部分成本占总量多少」，不是「新技术比旧技术先进多少」。</Notation>

# 八步实施方法

下次再遇到「层级/递归 + 透视 + 分页」这类需求，按这八步走。左边四步负责把它做出来，右边四步负责证明它站得住。具体的环境坑（AMDP 注释规则、FM 出参类型、传输后的 RFC 报错等）都收在文末的踩坑清单里，这里只留通用动作。

![可复用的八步实施流程：先做出来，再证明它站得住](https://img.jack-liang.com/sap-org-hierarchy-amdp-vs-abap/implementation-sop.svg)

## 第一步：先把口径跑对

不要一上来就搭框架、建对象、写接口。先用最朴素的方式——一段裸 SQL、一个临时脚本——把结果完整算出来，拿一份业务台账逐格核对。

**判据**：结果跟业务认可的数据一致，包括那些「层级列为空」的边界行。

这一步两小时，能省掉后面两天。算法错了，后面所有性能数字都是在给错的东西计时。

## 第二步：先验证可行性，再投入

这部分最容易白干。动手之前先确认两件事：

- **版本与特性**：想用的高级特性在当前版本上真的可用（这次的教训是 CDS 层级视图要 7.55+，一条路直接断了）
- **对象能否落地**：需要的各类对象在你的开发流程里真的建得出来、传得出去

**判据**：十分钟内真的建出一个空壳对象，别等写完几百行才发现无处安放。

## 第三步：先跑通，再优化

第一版怎么直白怎么写，不追求性能，让「输入 → 正确输出」这条链路先完整存在。

**判据**：端到端能出正确结果，慢可以接受。

没有靶子的优化是空转，这个能跑通的笨版本就是靶子。

## 第四步：对外接口端到端验证一次

结果要暴露给外部调用，就尽早从真实的调用方路径完整调一次，而不是只在开发工具里自测。接口层的坑有一个共性：**本地全是通的，外部全是断的**。

**判据**：从真实调用方发起一次完整调用，拿到正确结果。

## 第五步：写一份对照实现

用最不同的技术路线再写一版，不为上生产，只当尺子和应急备胎。

**判据**：两版结果整表完全相等。这一步同时能抓出精度问题、空值处理差异、排序不稳定——比任何人肉核对都靠得住。

没有对照版，你没法判断「快」是真的还是错觉。

## 第六步：交替基准，别分开跑

几版实现放在同一个循环里背靠背跑，剔掉第一轮（冷启动），取最小值。

分开跑会吃机器漂移——我第一次分开跑，同一份代码两次差 20%，差点得出错误结论。交替跑之后，各版共享同一个时间窗口的机器状态，比值才可信。

**判据**：跑间抖动要明显小于实现之间的差距。抖动 5%、差距 3%，这个结论就不成立。

顺便：比耗时更早暴露问题的是**行数**和**唯一 id 数**。先把这两个对上，再看时间。

## 第七步：三层校验，缺一不可

| 校验 | 防的是什么 |
|---|---|
| 逐页 diff（翻完全部页） | 分页偏移错位、页与页重叠 |
| 整表逐列比对 | 某一列语义写错、精度丢失 |
| 跨页唯一 id 数 = 接口返回的总数 | 漏行、重行（专治「最后一页多回一行」） |

我这次的偏差就是被第三项抓出来的：接口返回总数 10,113，实际唯一 id 10,112。

## 第八步：换环境必须复测

不同环境的数据量可能差一个数量级，结论经常整个翻过来。这次开发机上 13 ms 的回退没人察觉，测试机上就是 78 ms。凡是「在 A 环境成立」的结论，到 B 环境的第一件事就是重测，别默认它还在。

**判据**：关键结论在目标环境重新测过一遍，而不是从旧环境推过去的。

## 选型判据

| 条件 | 选什么 |
|---|---|
| 行数 < 3,000、调用频繁、要求低延迟 | 纯 ABAP（甚至干脆在应用层加缓存） |
| 行数 1 万+、要分页、并发用户多 | AMDP（内存与并发优势比耗时优势更实在） |
| 要按组织下钻、子树常达几千上万节点 | AMDP + HIERARCHY（省 10%～17%） |
| 外部系统要 RFC 直调 | 都得包 FM，出参行类型必须是表类型 |

# 踩坑清单

| 坑 | 现象 | 解法 |
|---|---|---|
| AMDP 里写中文注释 | `W: Only ASCII 7 bit characters` | 注释全改英文 |
| AMDP 注释里有单引号 | 「不允许占用超过一行的文字」 | 去掉 `'`，改写成 `of the` |
| 带参表函数的 `P_CLIENT` 不自动填 | 数据一行都出不来 | 显式传 `$session.client` |
| FM 出参行类型用了结构 | `rfc_enabled` 失败、`FMODE` 为空 | 建 DDIC 表类型指向它 |
| FM 出参行类型用了 CDS 视图 | `declares no type` | 必须 DDIC 表/结构/表类型 |
| `HIERARCHY` 的 `source()` 里放 union | `invalid column name: NODE_ID` | source 里只放一个 select |
| `start where node_id = 起点` | 顶层组织一行都出不来 | 改 `start where parent_id = 起点` |
| `HIERARCHY` 不加 `multiparent` | 多父节点的组织直接报错 | 显式加 `multiparent` |
| `where exists` 求交 | 成本随行数线性上涨 | 下推进集合构造，用一次 join 换掉 |
| 传输后调用 AMDP 过程 | `RFC_CLOSED` | 调用前 `COMMIT WORK.` |

另有一个**实验环境的坑**，跟 SAP 对象无关但很坑人：用网关验证全量时，单表返回被截到 10,000 行，而 `EV_TOTAL` 仍是真实值，响应里也没有截断标记。所以「行数对不上」的时候先怀疑工具链——验证全量一定要分页拉。

# 最后

这次做完，我对「下推」这件事的理解变了一点。

以前我的默认判断是「计算下推到数据库总是更优」，因为减少了数据传输。但这次的数据说明：**下推的收益等于「被下推掉的那部分成本在总量里的占比」**，而占比取决于算法结构，不取决于数据量本身。

在这份需求里，真正能被下推消掉的只有 BFS 圈子树这一块（下钻时省 17%，全量时只省 2%）；祖先展开、透视、分页（还得先物化总数）挪到数据库里照样要算。能消掉的满打满算只有三分之一，所以 AMDP 在 1 万行上最多只能追平。

反过来，如果瓶颈正好在那三分之一里——比如下钻场景，递归真的一层层往下走——AMDP 就开始赢了。这次也是唯一一处它赢的地方。

所以选型的正确问法不是「哪个技术更新」，而是「**我的耗时分布在哪一层，那一层能不能被搬走**」。先把这句话答清楚，再决定用 AMDP、HIERARCHY 还是老老实实写 ABAP 循环。

三个版本、三轮分页重构、两轮传输复测之后，最值钱的产出其实不是那个 76 ms 的数字，而是那张八步流程——它下次能让我少走两天的弯路。
