> **系列说明**：这个系列写我在开发里反复验证过的基本规律。不追新概念，只讲那些早晚会再次应验的东西。

> **TL;DR**：数据有几种情况，代码就要有几种应对。
>
> 写 ALV 报表时，我脑子里只跑了 happy path：数据有、金额有、找得到。上线一周
> dump——业务筛了"只看本月"，分母为
> 0。这篇讲一个反直觉的判断：空、零、找不到不是"特殊情况"，是数据常态。提供一个判断标准 +

## 一、上线一周的除零 dump

刚做开发时交付一张 ALV
报表，按客户算交付达成率：分子是已交付数量，分母是计划数量，相除。

我自己测的几组数据都正常。上线一周，dump：因为除零。

排查倒不复杂：业务同事习惯筛"只看本月"，有一家新客户本月刚建档，计划数量是
0——分母为 0，dump。

更难受的是，这不算孤例。往前翻，我至少还踩过两次同类的坑：

- `READ TABLE itab INTO wa WITH KEY kunnr = lv_kunnr.` 没判 `sy-subrc`，READ
  没找到，`wa` 里还是上一次的值——程序不报错，只是数据悄悄错了
- `SELECT SINGLE ...` 查一条配置没查到，字段沿用了上一次的——同样不报错

这两次的共同点是：我以为不会发生的事，业务里天天发生。

我以前写代码，脑子里跑的是 happy
path：数据有、金额有、字段有、找得到。但**"如果没数据怎么办"**这类问题，你认真想过吗。

## 二、数据有几种情况，代码就要有几种应对

这句话可以拆开看。

**数据有几种情况**，是业务告诉你的。空、零、负、超长、特殊字符、查不到——这些可能性不是靠拍脑袋，是去问：这个字段可能为空吗？金额可能为负吗？这个
SELECT 可能没结果吗？和业务聊 15 分钟，清单就出来了。

**代码有几种应对**，是你写出来的。每种情况，代码里要有一个分支接住：

- 不能默认内表不为空 → `IF itab IS NOT INITIAL.`
- 不能默认 SELECT 找得到 → 判 `sy-subrc = 0`
- 不能默认金额大于零 → 除法前保护分母
- 不能默认用户填了必填 → Dynpro 的 FIELD 校验

两种情况两种应对，三种情况三种应对。少一个应对，就少一个边界保护——漏掉的那个，上线后由业务帮你"测试"。

你可能想问：情况列出来了，每种该怎么处理？报错还是放行？

判断标准只有一条：这件事业务上"应该发生"还是"不应该发生"。

- 不应该发生的，报错：必填字段为空、主键重复、金额为负（业务不允许）
- 应该发生的，放行：本月没数据就显示空表、查不到就显示无结果

"报错"不是跟业务过不去，是把边界明确化——让业务知道这种情况不该发生，下次提需求就会带上它。反过来，对允许发生的情况乱报错，业务会被训练成忽略你的报错。

你可能觉得：业务自己也没想清楚，问了也白问。我的经验正相反：问不出来的，当场让他选——报错还是放行。他选不出来，就报错。把问题暴露出来，比让它藏在数据里强。

## 三、结构工程师不算"平时压多少"

开发之外，把边界当起点的人比比皆是，结构工程师是其中最彻底的。

设计院算一栋楼的荷载，算的不是"平时压多少"，是"最多压多少"。抗震按设防烈度，屋顶按百年一遇的雪载，梁柱按最不利的组合。日常荷载决定楼住得舒不舒服，最坏荷载决定楼倒不倒。

反过来，如果设计只按日常荷载做，再逐层补"安全检查"，那栋楼你敢住吗？

写代码一样。happy path
决定功能演示顺不顺，边界处理决定上线后活不活。上线那一刻，程序面对的就是最坏荷载。

## 四、动手前和动手后各 5 分钟

动手前，和业务把这 4 个问题聊完：

1. 数据从哪来、谁产生、什么格式
2. 有哪些可能的情况（空 / 零 / 负 / 超长 / 查不到）
3. 哪些情况不该发生——报错
4. 哪些情况允许发生——放行

动手后，提交前过这张清单，每条 5 到 10 秒：

1. 每种数据情况都问过业务，不是我自己猜的
2. 每个分支都有对应处理（判 `sy-subrc`、`IS INITIAL`、除零保护）
3. "不该发生"的情况报错了，"允许发生"的情况放行了
4. 放行的情况有明确的界面显示或日志，不留"上一次的值"
5. 没有"catch 之后继续跑"的静默放行

第 5 条单独说：边界处理不等于到处 try-catch
把异常吞掉，那和没处理一样——程序不报错，只是错得更隐蔽。这和 05
篇是同一个思想的两半：05 讲失败发生后消息别丢，06 讲失败发生前把边界想到。

反模式也简单：写完代码直接丢给
QA，自己没有先过一遍。上线后才发现的边界问题，是开发者的疏忽，不是 QA 的责任。

## 五、写在最后

**先定界，再写码。**

别替数据做主。"想当然地默认"是 bug
的温床：你以为理所当然的分母，在业务手里可能就是 0。

下一篇聊测试。06 讲"想到边界"，07 讲"测到边界"——想到的边界怎么用 ABAP Unit
固化下来，让以后每次改动都被自动检查一遍。
