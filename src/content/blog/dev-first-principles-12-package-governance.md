> **系列说明**：这个系列写我在开发里反复验证过的基本规律。不追新概念，只讲那些早晚会再次应验的东西。

> **TL;DR**：规范不是写出来的，是被执行出来的。
>
> 有一次把一个包从 dev 传到生产，按"只传这一个包"操作，发布后生产挂了：这个包里的函数调了另一个包的 Data Element，那个包没传，所有用到它的报表全部 dump。包间引用的规范其实早就发过，只是没人执行。这篇讲两个反直觉判断：全局可见不等于应该全局用；规则和执行是两件事。加五个做法和一份自查清单。

---

## 一、只传了一个包，生产挂了

有一次把一个包从 dev 系统迁到生产。

操作本身很规矩：按清单只传这一个包，发布前检查，也没报错。

生产挂了。

排查下来原因不复杂：这个包里一个自开发函数，用了另一个包里定义的 Data Element ZFI_BUKRS。另一个包不在传输清单里，生产上这个对象根本不存在，所有调用这个函数的报表，运行即 dump。

麻烦在第二步：我想查"到底还有哪些地方引用了包外的对象"，发现查不全。SE80 里能看到包内的结构，看不到完整的依赖图；剩下的办法是全局搜代码、问老员工、猜。最后靠几轮 grep、问了几个人，才凑出一份"这次可能还缺什么"的清单，灰头土脸地补传。

更有意思的是事后复盘。包间引用的规范其实早就发过：Data Element 按业务域归属，跨包引用先登记。文档不短，道理也清楚。但出事之前，没人按它做——建对象的时候随手建，没人管它在哪个包；规范躺在 Wiki 里，没有一道工序拦得住不按规范建的对象。

我以前觉得，规范发出来、大家学习过了，就算立住了。这次之后明白：发规范是规则的事，执行是另一套系统的事。规则画得再漂亮，没有执行机制，就等于没有。

## 二、两个反直觉判断

第一个：全局可见，不等于应该全局用。

ABAP 的数据字典是全局的：Data Element、Domain、消息类、搜索帮助，在任何包里都直接用。建一次，处处可用，听着很方便。方便的代价是：这个对象归哪个包、谁负责改，没人知道。它脱离了包，也就脱离了治理——建的时候没人拦，迁移的时候才知道疼，就像我那次。

判断公共对象放哪，三个问题：会被谁改？业务口改的归业务域，技术口改的归基础层。业务归属是谁？归属财务域就待财务域，不能因为销售也会用就放进销售包。五年不变吗？货币、日期这种才进基础层；会变的一律留在业务域。

按这三问，结构分三层就够：

```
ZCOMMON_BASE         （基础层：货币、日期、消息类，几乎不变）
├── ZFI_COMMON      （财务域共享：客户、组织架构）
│   ├── ZFI_AR      （应收）
│   ├── ZFI_AP      （应付）
│   └── ZFI_GL      （总账）
├── ZMM_COMMON      （物料域共享）
│   ├── ZMM_PO      （采购订单）
│   └── ZMM_GI      （物料出库）
└── ZSD_COMMON      （销售域共享）
    └── ZSD_SO      （销售订单）
```

"大家都用"不是进 ZCOMMON_BASE 的理由。大家都用、但属于财务域，就去 ZFI_COMMON。ZCOMMON 大杂烩，是这次事故的远因。

第二个反直觉：规则和执行是两件事。

规则好定。命名规范、分层结构、归属判断，开个会画张图，半天搞定。执行难：开发赶时间顾不上，"我这种情况特殊"，code review 走形式。规则定得再好，没有人检查、没有环节拦截，就是不存在。上一篇说过，没人维护的文档比没文档更糟，规范是同样的道理：没人执行就等于没有——不，比没有更糟，它还给你一种"已经治理过了"的错觉。

你可能觉得：先把规范定完美了，再推给大家执行。

完美的规范落不了地。层级分五层、命名定到每个前缀、流程画成泳道图——推行成本太高，三个月就没人理。先分好"基础层 / 业务域"这两层，接受七成一致，比零规范强得多。

## 三、没有摄像头的路口，红绿灯靠自觉

交通规则里最说明问题的是摄像头。

红绿灯是规则，谁都看得懂：红灯停。但只装红绿灯不装摄像头的路口，大家心里都清楚——瞄一眼没车，就过了。规则在那里，执行不在，规则就退化成建议。

后来路口装了摄像头，闯红灯从"没人看见就没事"变成"必被记录"。行为立刻变了。不是大家忽然变自觉了，是执行的环节补齐了。

包治理一模一样。规范文档是红绿灯，ATC 检查和传输前的强制检查是摄像头。指望开发者自觉，和指望司机在没有摄像头的路口永远停住，是同一种指望。

## 四、五个做法

落到 ABAP，按见效速度排。

**1. 用 ATC 把规则变成检查**。SAP 自带的 ATC（ABAP Test Cockpit）能检查命名规范、对象归属、禁用语句、性能问题。把包间引用的规则编成检查变体，传输请求释放前必须跑过——检查不过，请求发不出去。人记不住的事，工具记得住；人不好意思拦的，工具拦得理所当然。这条是五条里最该先做的：功能现成，不花钱，只是大部分团队没配。

你可能想问：存量对象那么多，ATC 一开刷出几千条违规，怎么办？先只拦新增：存量设成基线，新对象全量检查。治理从来是增量的事，一口吃不成三层结构。

**2. 在必经之路设卡**。传输释放前强制 Code Review，关键对象——Data Element、Domain、消息类——必须有第二个人看过。关键是"不 review 不能传"这六个字——没有强制，review 一定走形式；走形式的 review 不如不 review。

**3. 让规范长在显眼处**。规则不该躺在 Wiki 里，该长在开发者天天看的地方：包描述写清"这里放什么、不放什么"，包级 README 一页（[11 篇](/blog/dev-first-principles-11-docs-and-code/) 那套），建对象时的包选择界面能看到的提醒。打开就能看到，比"我发过一份文档"有效得多。

**4. 渐进式接受**。第一步只分两层：基础层和业务域，其他不动。跑顺了再往下分。每个季度 review 一次公共对象的归属，把挪错的归位。归位是补救，防错靠机制——后者才值得花力气。

**5. 把规则编进新建对象的流程**。新人第一次建 Data Element，带他的人当面问一遍：放哪个包？为什么？这一问比发十份规范文档管用。一次带教形成肌肉记忆，规范从此长在人身上。

自查清单，Code Review 时过一遍：

1. 传输请求释放前强制过 ATC，检查不过不发
2. Data Element、Domain 这类关键对象强制 Code Review
3. 公共对象按三层归属，没有 ZCOMMON 大杂烩
4. 包描述写清了放什么、不放什么
5. 新人建第一个公共对象时走过"放哪个包"这一问

反模式也说一句：五十页规范文档加全员自觉——这两个词放在一起，就是"没有规范"的另一种写法。

## 五、写在最后

**规范不是写出来的，是被执行出来的。**

全局可见是 ABAP 数据字典的特性，不是可以随便引用的许可证。归属清楚了，迁移的时候才知道该传什么；执行机制在了，规范才真的存在。

[11 篇](/blog/dev-first-principles-11-docs-and-code/) 讲文档和代码共生，这篇讲包与包的关系治理——前十一篇讲个体怎么写好，这篇讲个体之间的关系怎么管住。到这里，排障、失败处理、测试、信息可被找到，前 12 篇的体系闭环了。

下一篇想换个软一点的话题——比如"对标准程序的敬畏"，或者"先让程序能跑，再让程序好改"。硬的基础打完了，后面聊软的实践。
