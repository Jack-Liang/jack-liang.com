> **系列说明**：这个系列写我在开发里反复验证过的基本规律。不追新概念，只讲那些早晚会再次应验的东西。

> **TL;DR**：没人维护的文档比没文档更糟。
>
> 有一次带新人接手项目。他先翻 Confluence，照着几十页功能说明去改 bug，改完发现代码早不是文档写的那样。又去看 SE11 的 Data Element 文档——空的。他花了两周才搞清楚哪些文档可信、哪些不可信。这篇讲一个判断维度：维护成本。改代码时顺手就维护的文档不会过时；分开维护的，从第一天起就在过期。加三条做法和一份自查清单。

---

## 一、照着文档改，改完发现不是那样

有一次带一个新人接手项目维护。

他很认真，第一步先去翻 Confluence。项目文档确实全：功能说明、接口说明、操作手册，洋洋洒洒几百页。他挑了一篇对着改一个 bug——改完测试，发现和文档说的不是一回事。代码改过几轮，文档还是最初那版。

他回来问我：文档不可信，那什么可信？我说你去看 SE11，看 Data Element 的文档。他去了，回来说：基本是空的。消息类的文本也是过时的，程序里几乎没注释。

最后他花了差不多两周，才把这套系统摸清楚：哪些 Confluence 页面是有人维护的、哪些早废了，哪些字段看 F1 就有说明、哪些只能去问业务。这两周本身就是纯浪费——不是他慢，是系统里那堆过期文档在主动误导他。

我以前觉得，文档写得越详细越好，新人看着文档就能上手。那次之后改了看法：没人维护的文档比没文档更糟。没文档，新人知道去问；有错文档，新人照着错路走，还要先发现文档骗了他。

## 二、判断标准只有一个：维护成本

一份文档会不会过时，不看写得好不好，看一件事：改代码的时候，改它顺不顺手。

顺着这个维度，信息分三类。第一类，写代码的时候顺手就写了的：字段的 Data Element 文档，类和方法的 ABAP Doc，消息类的文本，表和包的短文本。这类和代码绑在一起，改代码必然碰到它，不会过期。第二类，业务变更时才需要改的：架构决策、业务规则、已知坑。这类改动频率低，放在项目级的 README 里，跟着版本走。第三类，改代码时完全碰不到的：跨团队约定、项目背景、会议结论。这类只能放 Confluence，放的时候就要想清楚谁来维护。

关键就一个词：绑定。SAP 里的那批文档工具——Data Element、ABAP Doc、消息类、搜索帮助、测试类——功能上没什么惊艳的，真正值钱的是它们和代码存在同一个地方。改字段必然看到 Data Element 文档，改消息必然看到消息文本。文档和代码分开维护的那一天起，过期就开始倒计时。

所以比例大致是：八成信息放 SAP 内，一成半放项目 README，剩下半成放外部。大部分团队是反过来的——Confluence 几百页，SE11 里一片空白。

你可能想问：架构决策为什么不写进代码里？命名和结构能告诉你系统是什么，说不出当初为什么这么做。为什么不用 BAPI 直接调底层表、为什么按应收应付分而不是按模块分——这些是决策时的权衡，代码里读不出来，必须有人记下来。但它们改动极少，一年改不了几次，README 够用。

## 三、病历合到一个人身上，才不会丢

病历以前不是一份的。门诊一份，住院一份，检验科一堆报告单，各记各的，互不相通。医生看病人的时候，手里永远是不全的那部分：不知道病人上个月住过院，不知道某项检查刚做过，重复开单、误诊，都出在这个"信息分散"上。

后来医院陆续把病历合并：一个人的所有记录归到一个档案里，跟着这个人走。记录归到人身上，才保证了看的时候一定在。

文档也一样。信息归到代码身上——Data Element 归到字段上，ABAP Doc 归到方法上——读代码的时候它一定在。归到 Confluence 上，读代码的时候它大概率不在，在也可能已经过期了。

## 四、三条做法

落到 ABAP，按收益排。

**1. 能放 SAP 内的全放 SAP 内**。写代码时顺手做的几件事：字段建 Data Element，DOCUMENTATION 写上；类和方法写 ABAP Doc；消息走消息类，不写硬编码文本；表和包把短文本、长文本填了；有取值范围的字段挂搜索帮助。这几件事的成本几乎为零，因为它们就在你建对象的那个屏幕上。测试类也算文档——一段带预期输出的测试代码，比一页接口说明有用得多。

**2. README 只写代码说不出的**。包级 README 不写功能，功能代码自己会说。只写三类：架构决策（为什么这么做）、业务规则（顾问确认过的口径）、已知坑（issue 链接）。三五节就够，一个包一页。

```markdown
# 包 ZFI_AR（应收）

## 架构决策

- 为什么按"应收/应付/总账"分子包：业务域稳定，技术会变
- 为什么不用 BAPI 直接调底层表：见 ISSUE-2024-03

## 业务规则

- 发票必须在创建后 30 天内过账（业务顾问 2024-01 邮件确认）

## 已知坑

- 改税率时必须同步更新 ZTC_FI_CONFIG，见 09 篇
```

**3. 外部文档只留跨团队信息**。需要给别的团队看的——接口约定、项目背景、会议结论——放 Confluence，写的时候注明负责人和最后确认日期。凡是只有自己团队用的功能说明，别写，写了也没人维护。

你可能觉得：Confluence 上那些页面写都写了，删了可惜。

可惜的是继续留着。它们现在的作用是坑下一个新人。要么认领下来维护，要么标上"已过期，勿参考"——最怕的是既不维护也不标注，看着像真的。

自查清单，Code Review 时过一遍：

1. 新字段建了 Data Element，DOCUMENTATION 写了
2. 公开的类和方法有 ABAP Doc，参数和异常说清了
3. 消息文本走消息类，没有硬编码在程序里
4. 包级 README 只写架构决策、业务规则、已知坑
5. Confluence 功能说明不再新增，只留跨团队信息

反模式也说一句：文档和代码分两处维护——从分开那天起，过期就不是"会不会"的问题，是"多快"的问题。

## 五、写在最后

**没人维护的文档比没文档更糟——它会误导下一个相信它的人。**

[10 篇](/blog/dev-first-principles-10-self-describing-code/) 说代码可以是文档，这篇说剩下的文档放哪：跟着代码走的那部分，永远不会过期；单独供起来的那部分，从第一天起就在倒计时。

下一篇聊最后一种被埋没的信息：包和包之间的关系。包结构整理得再好，跨包的引用没人治理，迁移的时候照样拔出萝卜带出泥。
