之前写过一篇[能跑在笔记本中的 SAP 系统](/blog/abap-cloud-developer-trial/)，介绍过 SAP 的 ABAP 试用容器：一台笔记本就能跑一套完整的 ABAP Cloud 开发环境（ABAP Stack + HANA），对自学 ABAP Cloud 的人来说是不可替代的玩具。

坏消息是：**2026 年 11 月 17 日起，这个试用镜像从 Docker Hub 和 SAP Cloud Appliance Library 全面下架**，配套的 minisap 临时许可申请入口也同步关闭了。好消息是：本地镜像还在的机器上，容器依然可以救活，而且过程里有一些查遍全网都找不到的发现，值得记录。

## 现象：重建容器后，许可失效了

我的容器 a4h-2025 是今年 8 月底装的，用的是 minisap 申请的临时许可（SAP 的试用许可只有三个月寿命，到期要去 minisap 重新申请）。11 月中旬我重建了一个新容器，按照社区惯例固定了 MAC 地址——因为大家都知道 **SAP 的 Hardware Key（许可绑定的硬件指纹）是从网络卡信息派生的**。

然后诡异的事情发生了：

| 容器                         | MAC 地址          | Hardware Key |
| ---------------------------- | ----------------- | ------------ |
| 旧容器（11月初，许可申请时） | be:a8:ce:35:64:20 | Z0906102924  |
| 旧容器（重启后）             | be:a8:ce:35:64:20 | F0303562953  |
| 新容器                       | be:a8:ce:35:64:20 | I0175959389  |

**同一个 MAC 地址，三个不同的 Hardware Key。** 旧许可在新 key 上直接失效，而 minisap 的 A4H 申请入口也随下架一起关闭了——官方渠道全断，系统变成孤儿。

## 排查：MAC 固定为什么没用

第一反应是怀疑自己哪里做错了，但反复核对：MAC 一致、hostname 一致、IP 一致，key 就是变。翻许可库（SAPLIKEY 表）找线索的时候发现了一个很有说服力的证据：**表里躺着几十个不同 Hardware Key 的许可检查记录，全是镜像构建时期留下的**——也就是说 SAP 自己的构建管线里，同一个镜像在几十个环境里产生的 key 也各不相同。

结论：**Hardware Key 的派生不止依赖 MAC**，它绑定的是容器实例和运行环境的组合（宿主内核、运行时状态都有嫌疑）。固定 MAC 能消除一个变量，但消不掉所有变量。社区流传的『固定 MAC 就能保住许可』在老版本镜像或 Linux 原生 Docker 上可能成立，在 Docker Desktop + Apple Silicon 这套组合上不成立。

## 插曲：双容器并发会踩的网络坑

排查期间还踩了一个和许可无关但更隐蔽的坑：新容器启动时，旧容器还在运行。两个容器的 MAC 和发布端口完全相同，结果是**后启动的容器网络端点挂载失败**——容器能起来，但没有网络。

这个状态非常隐蔽：容器健康、进程都在，但 ABAP 的消息服务器启动时直接报错退出，日志里的关键是这一行：

```
*** ERROR => NiHL6OSLookupNameToAddr: NiPGetHostByName(vhcala4hci) failed
```

主机名解析失败的原因是 **/etc/hosts 里缺少了主机名条目**（正常情况下 Docker 会在启动时写入 `172.17.0.x vhcala4hci` 这一行），而 hosts 缺行的原因又是网络端点没挂上。三层因果叠在一起，第一次遇到很难定位。

修复方法：确保另一个容器停止后，重新挂载网络并重启——

```bash
docker network connect bridge a4h-2025
docker restart a4h-2025
```

重挂载会持久化到容器配置里，之后重启就不会再丢。

## 意外发现：内核会自己签许可

把网络修好之后，真正的惊喜来了。a4h-2025 的 Hardware Key 因为网络端点重建又变了一次（变成了 R0258830004），按理说系统应该继续处于无许可状态——但 ABAP 栈完整启动了，许可状态全部 **valid**：

```
Hardware Key          : R0258830004
Software Product      : NetWeaver_HDB
Type of License Key   : temporary
Begin of Validity     : 20261119
End   of Validity     : 20261217
Validity              : valid
```

查许可库才发现：**ABAP 内核在工作进程启动的许可检查路径上，会自动为当前的 Hardware Key 签发一套临时许可**（NetWeaver_HDB 28 天 + Maintenance_HDB 60 天）。也就是说 Hardware Key 漂移之后，系统重启一次，内核很大概率会**自愈**——自己给自己签一套新的临时许可。

这个行为我翻遍了 SAP 社区和 FAQ 都没找到记载，但它解释了一个现象：很多容器用户会发现『重建容器之后莫名其妙又能用了』。

## 逆向：把签名方案挖出来

自愈机制能让系统活下来，但我想知道**签名本身是怎么算的**——如果能独立复现，就不再依赖任何 SAP 组件。目标二进制是 `saplikey`：13MB 的 ELF，好在带完整符号表。本地 Ghidra 桥接当时有问题，全程用 objdump 的符号表 + 反汇编搞定。

定位调用链花了主要功夫：在符号表里沿许可相关函数往下钻，找到一条三级调用链——

```
likeyind_make_temporary_likey      装配临时许可结构（字段、日期、系统号）
  └─ get_to_be_signed_format_sensitiv   把字段拼成『待签串』（定宽 + 空格填充）
      └─ likeyind_calculate_fingerprint   对待签串算指纹（即签名）
```

指纹函数的反汇编非常有礼貌：`haMD5Init` → 两段输入各做一次 UTF-8 转换后分别 `haMD5Update` → `haMD5Final` → base64 编码。也就是说**签名就是一次 MD5**——第一段输入是待签串的 UTF-8 字节，第二段是藏在 `.rodata` 里的一个固定常量（盐）。

待签串的装配逻辑是整个逆向里最费工的部分：字段以『指针 + 长度』对数组的形式组织，SIMD 指令做定宽空格填充，中间还有按产品名分叉的分支处理。这部分没有逐条硬读汇编——用了一个更快的办法：**测试向量驱动**。许可库里躺着内核自己签出的许可行，字段和签名都在；把字段按各种拼接顺序、宽度、编码穷举组合，与签名逐一比对，穷举到某个组合时 MD5 逐字节命中，格式就确定了。再拿另一条内核签发的许可行交叉验证，同样命中。

最终结论：指纹 = MD5(字段规范拼接 ‖ 固定盐)，无 HMAC、无密钥。签名常量、拼接的精确规格与生成器代码，不在此展开。

## 解决方案的分层

自愈不是每次都可靠（比如镜像刚装好、内核还没跑过许可检查的第一次启动），所以我做了三层方案。这里只说思路，具体实现不在文中展开：

1. **内核原生自签（首选，零维护）**：利用上面发现的自愈机制——每次 key 变化后正常重启一次容器，让内核自己签。实测 a4h-2025 就是靠这个恢复的。
2. **独立签名生成器（方案 B，纯 Python）**：逆向了临时许可的签名方案之后，写了一个不依赖任何 SAP 组件的生成器——任意有效期、任意字段组合，产出可以直接入库的标准许可行。已用内核自己生成的许可做逐字节验证，内核完全接受。
3. **内核原生路径补丁（方案 A，保险）**：给 saplikey 的自签入口绕过一个前置守卫，让内核用自己的签名器为当前机器签发许可。作为 B 失效时的保险（比如未来换用不同内核构建的镜像）。

三层方案互相独立，日常根本用不上——容器里的 10 年期许可装好之后，这件事就结束了。

## 关于边界的说明

两句话：自己逆向研究、成果私有保存，在多数法域属于可辩护的学习行为；公开传播可运行的绕过工具则是另一回事——所以签名常量与生成器不在公开范围内。另外，这个产品的官方许可本来就是三个月一签的临时许可，从不存在『永久许可』；用它自己的临时许可机制保住一个官方已停止分发、关闭许可渠道的免费学习系统，是最贴合原意的保存方式。

## 经验总结

- **固定 MAC 不是许可的护身符**：Hardware Key 绑定的是容器实例与环境的组合，key 漂移是常态。别再和 MAC 较劲，方案设计要假设 key 随时变。
- **许可丢了先重启容器再说**：内核的自愈路径可能直接救活，一行命令的事。
- **多容器同镜像部署时，MAC/端口冲突会让后启动者丢网络**：症状是『容器活着但主机名解析失败』，修复用 `docker network connect`。
- **镜像记得备份**：下架之后，`sapse/abap-cloud-developer-trial:2025` 这个镜像就是绝版。`docker save` 一份到冷存储，比任何许可方案都重要。

如果你也在维护这套试用容器、遇到了许可问题，希望这篇的排查路径能帮你少走弯路——官方渠道虽然关了，但这个学习系统还远没到寿命终点。
