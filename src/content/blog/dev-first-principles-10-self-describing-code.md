> **TL;DR**：好的代码组织自带导航。

## 一、ZMM_PO 一搜出来十几个程序

有一次接手一个项目的维护。

第一个任务是改"采购订单的审批逻辑"。先去翻文档，文档里写着：在 ZMM_PO
程序里。打开 SE38 一搜
ZMM_PO——出来十几个程序：ZMM_PO、ZMM_PO_OLD、ZMM_PO_NEW、ZMM_PO_2、ZMM_PO_BAK。

哪个是审批？不知道。每个都打开看看？十几个程序，每个几千行，不可能。

最后是老员工口头指路：在 ZMM_PO_RELEASE 函数组里，函数
Z_MM_PO_RELEASE_CHECK。我顺着找过去，果然在那里。

问题是，这条路径只存在于老员工脑子里。他哪天离职了，下一个接手的人还是从十几个
ZMM_PO 开始翻。

我以前觉得，代码怎么组织是程序员自己顺手的事，真正给接手的人看的，是文档。后来发现不对。文档会过期——ZMM_PO
程序改了八回，文档还是最初那版；代码组织不会过期，它天天被执行。哪份信息更可信，不用争。

## 二、命名、结构、职责，各管一件事

那次之后我反过来想：如果代码组织得好，那个接手的人需要文档吗？

不需要。他要找审批逻辑，只需要三层信息：名字告诉他这是什么，位置告诉他这在哪，职责告诉他这该管什么。自我描述的代码，就是把这三层都做对。

命名写"是什么"，不写"怎么做"。create_invoice 是对的，loop_insert_buffer_write
是错的——后者把实现方式烙在了名字里，实现一换，名字就撒谎。命名对了，调用者只看名字就够了，80%
的"读代码"根本不用发生。

结构按业务域，不按技术分层。包就是目录，路径读出来就该是"在干什么"：财务的发票创建，就该待在
ZFI_AR 下面。

职责一个对象一个。这是
[《02 篇 复杂问题，要先学会「切」》](/blog/dev-first-principles-02-divide-by-responsibility/)
讲过的按职责切：一个函数、一个类只做一件事。名字、位置、职责三层叠在一起，一个陌生人看一眼，就知道这东西是什么、在哪、该干什么。

你可能觉得：起名字、理包结构太花时间了，ZPROG01 也一样能跑。

跑是一样跑，找不一样。代码的一生，写一次，读几十次。花在命名和结构上的时间，读的那几十次会连本带利还回来。

## 三、图书馆没有导览手册

这事图书馆几百年前就解决了。

一个藏书百万的图书馆，读者进门，没有导览手册，也不需要管理员领着。中图法把全馆分成二十二个大类：A
马克思主义，B 哲学，I 文学，T
工业技术，每个大类再往下细分，一层一层，直到书架上的某一格。每本书的书脊上印着编号，编号就是它的地址。

读者找书，靠的就是这套编号。管理员新上一批书，按编号归入对应的格——维护成本几乎为零，因为归类发生在书进馆的那一刻，跟着书走。

书脊编号就是命名，书架层级就是包结构。书自己带着地址，所以不需要一本《本馆藏书使用手册》——真写了这么一本，三个月就过期。

代码也一样。命名和结构做到位，代码自己带着地址；做不到位，才需要靠文档和口口相传。而后者的保质期，取决于写文档的人还在不在职。

## 四、三条做法

落到 ABAP，按重要性排。

**1. 包结构按业务域**。SE80
的包本身就是导航系统，别浪费它。这套命名读出来就是"在做什么"：

```
顶层包     ZFI / ZMM / ZSD           (财务/物料/销售)
子包       ZFI_AR / ZFI_AP / ZFI_GL  (应收/应付/总账)
函数组     ZFG_AR_INVOICE
函数       ZFI_AR_INVOICE_CREATE     (应收发票创建)
类         ZCL_SD_ORDER
方法       CREATE( ) / VALIDATE( ) / SAVE( )
```

判断标准就一条：业务变更的时候，你知道去哪个包改吗？知道，结构就是对的；不知道，就回去重排。

**2. 命名即路径**。函数
ZFI_AR_INVOICE_CREATE，从名字能推出归属、业务、动作三层信息。反过来，zprog01、z_new
这种名字，等于宣布"不想让人找到"。命名规范不用复杂，一套前后缀约定（ZFI_ / ZCL_
/ ZFG_）加一条"写是什么不写怎么做"就够了。

**3.
注释写"为什么"，不写"做了什么"**。做了什么，代码自己会说；为什么这么做、有什么坑，代码说不出，这才是注释的地盘。

```abap
i = i + 1.        "i 加 1                  —— 多余，删了
i = i + 1.        "跳过表头，源文件格式见 issue #123  —— 留
```

你可能想问：注释到底写多少算多？判断方法也简单：这段注释如果删掉，读代码的人会少知道什么？答案是什么也不少，就删。

自查清单，Code Review 时过一遍：

1. 包结构按业务域分，不按 MVC 或技术分层
2. 函数、类、方法的命名能读出"是什么"，读不出实现方式
3. 一个函数只做一件事，名字里不带 process_data_v2_final 这种万能词
4. 注释解释"为什么"，不复述代码
5. 新对象建进包之前，先想它能从包路径里被找到吗

反模式也说一句：按 MVC
分包、命名随意、一个函数做五件事、注释写"做了什么"——这四件事的共同点是：都把找代码的活儿，推给了文档和别人的记忆。

## 五、写在最后

**代码可以是文档——前提是组织得好。**

文档必然过时，代码天天被执行——哪份更值得信任，答案一直在那儿。

[《09 篇 配置表泛滥怎么治理》](/blog/dev-first-principles-09-config-table-governance/)
把配置表收进登记册，这篇把代码变成自己的目录——干的还是同一件事：让信息待在能被找到的地方。
